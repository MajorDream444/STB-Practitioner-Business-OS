## TX-ROUTE-001 — Enquiry bypasses the tracked intake path

- **Pattern.** A call-to-action submits the visitor's details by opening the
  visitor's mail client addressed to a personal inbox, instead of sending them to
  the practitioner's tracked intake form and CRM.
- **Mechanism.** The enquiry never enters the system the practitioner uses to
  follow up, so there is no record, reminder or count. Whether this lost any real
  enquiry is **unmeasured**.
- **Detection.** Search conversion components for mail-client submission
  (assignment of a `mailto:` target to the window location) and trace every
  call-to-action to its destination.
- **Standard fix.** One routing function through which every enquiry passes;
  **no mail-client fallback by design**; it returns a result object and never
  throws; on failure it shows the visitor the form link and a copyable summary so
  nothing typed is lost.
- **Regression guard.** A test that scans components and fails if a
  mail-client submission reappears (plain contact links remain allowed), plus unit
  tests of the routing function. Passing at the post-fix commit (suite 64/64,
  reproduced in this session). **Limitation:** the scan matches only assignment
  of a mail-client target to the window location; other submission forms would
  pass it.
- **Evidence.** Defect: EQ1 — present in two components at the pre-fix commit,
  absent at post-fix. Guard: EQ2. `n = 1 build`.
- **Crosswalk (informal).** Conversion; Follow-up.

## TX-STATE-001 — Confirmation shown for a booking nothing can make

- **Pattern.** After a visitor submits a booking request, a screen tells them a
  space is secured or confirmed, though no scheduling system exists and nothing
  was reserved or sent.
- **Mechanism.** The visitor is told something false, and may rely on it. This is
  a consumer-protection concern as well as a quality defect (indicative; not legal
  advice).
- **Detection.** Read every success state and ask what system event it reports;
  if none, it is a false state. Walk the journey as a visitor and compare what is
  claimed with what the system recorded.
- **Standard fix.** Phrase the outcome as a *request* that the practitioner will
  answer; state what happens next in plain words; never confirm what the system
  cannot confirm (CLAUDE.md rule 4).
- **Regression guard.** **None found.** The reference suite's guards cover only
  mail-client submission and scarcity strings; the confirmation screen was fixed
  by rewriting the component, not by a test. A reusable guard would fail on
  confirmation wording in components that have no confirming back end. Not built.
- **Evidence.** EQ1: success-state wording present in the pre-fix component;
  no booking or scheduling system found in the build. `n = 1 build`.
- **Crosswalk (informal).** Conversion.

## TX-STATE-002 — Invented availability and scarcity

- **Pattern.** A booking picker shows fixed calendar dates, each labelled with a
  count of places remaining, with no connection to any real calendar.
- **Mechanism.** Scarcity that does not exist pressures visitors to act on false
  information, and the dates go stale. Indicative consumer-protection concern;
  not legal advice.
- **Detection.** Search for hard-coded dates and "N spots left" style strings;
  confirm that every availability claim is sourced from live data.
- **Standard fix.** Show no availability or scarcity unless it comes from a real
  scheduling source. Collect a coarse timing *preference* only, never a specific
  slot the system cannot honour.
- **Regression guard.** A test that fails if scarcity-style strings appear in
  components. Passing at the post-fix commit. **Limitation:** the pattern matches
  only "N spot(s) open/left/remaining"; other scarcity wording would pass it.
- **Evidence.** EQ1: five hard-coded date rows with scarcity labels at the
  pre-fix commit; none in components at post-fix. Guard: EQ2. `n = 1 build`
  (5 occurrences within it).
- **Crosswalk (informal).** Conversion.

## TX-DATA-001 — Health information collected without need

- **Pattern.** An enquiry or booking step asks the visitor to tick a checklist of
  physical or health symptoms before any relationship exists.
- **Mechanism.** Health data is special-category data (GDPR Art. 9). Collecting it
  needs a lawful basis and safeguards the practitioner may not have, and the
  diagnostic does not need it (CLAUDE.md rule 5).
- **Detection.** Review every form field and every free-text prompt; mark any
  that asks about health, symptoms, medication, or conditions.
- **Standard fix.** Remove the checklist. Replace with an optional free-text note
  that tells the visitor *not* to include medical or health details; the
  practitioner asks what they need in conversation.
- **Regression guard.** None implemented in the reference build. A reusable
  check would scan form definitions for health terms. **Not built** (rule 6).
- **Evidence.** EQ1: body-area checklist wording present at the pre-fix commit;
  absent at post-fix, where the replacement text discourages health details.
  `n = 1 build`.
- **Crosswalk (informal).** None; this is a privacy defect.

## TX-WIRE-001 — Conversion component built but never rendered

- **Pattern.** A booking component exists in the code base but nothing imports or
  mounts it, so no visitor can reach it.
- **Mechanism.** Effort and review attention go into a path that cannot be
  used, and audits of its code overstate its consequence. In the reference build
  this made the audit's "live revenue leak" claim wrong (C-001).
- **Detection.** For each conversion component, find where it is mounted in the
  built page; if nowhere, it is dead. Audit the *reachable* funnel first.
- **Standard fix.** Delete the dead component or mount it deliberately; audit
  severity must follow reachability.
- **Regression guard.** None implemented. A reachability check is possible; not
  built.
- **Evidence.** EQ1: the application root had no reference to the component at
  either the pre-fix or post-fix commit. `n = 1 build`.
- **Crosswalk (informal).** Conversion.

## TX-ASSET-001 — Missing asset hidden by a successful HTTP response

- **Pattern.** A single-page application serves its index page, with HTTP 200 and
  an HTML content type, for any unknown path, so a missing image appears to load
  and a naive status check passes.
- **Mechanism.** A broken image ships because the check looked at the status code
  rather than the content type.
- **Detection.** Request each declared asset and assert both a success status
  **and** an image content type, not HTML.
- **Standard fix.** Maintain an asset register and a test that asserts existence
  and content type of every declared asset.
- **Regression guard.** An asset-register test exists in the reference build; it
  was not found to assert content type, so the full guard is **unverified**.
- **Evidence.** **EQ0**: stated in the provenance record; not independently
  observed in this session. `n = 1 build`. Do not treat as established.
- **Crosswalk (informal).** Message.

## TX-QA-001 — Tests pass while the typecheck fails

- **Pattern.** The repository's test run passes while its typecheck script
  reports errors in the test files themselves (missing environment type
  declarations).
- **Mechanism.** The two gates disagree, so "green" depends on which one was run;
  the components called "proven" were only proven by one of them.
- **Detection.** Run the repository's own lint/typecheck and test scripts
  together, from a clean install.
- **Standard fix.** Include test files and their type packages in the typecheck
  configuration, and require both gates in one release check.
- **Regression guard.** None. Add one release check that runs both.
- **Evidence.** EQ2: reproduced in this session at the post-fix commit, clean
  install; tests passed (64/64) and the typecheck reported errors in test files.
  A version difference between the declared and the executed test runner was also
  observed and left unexplained. `n = 1 build`.
- **Crosswalk (informal).** Operations.
